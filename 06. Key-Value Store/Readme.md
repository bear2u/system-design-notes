# 6장: 키-값 저장소 설계

## 소개
**키-값 저장소(key-value store)**는 데이터를 키-값 쌍으로 저장하는 비관계형 데이터베이스의 한 종류입니다. 각 키는 고유하며 해당 키를 사용해 값에 접근합니다. 이 장에서는 다음과 같은 연산을 지원하는 확장 가능하고 고가용성을 갖춘 분산 키-값 저장소를 설계하는 방법을 설명합니다.
- 데이터 삽입: `put(key, value)`
- 데이터 조회: `get(key)`

### 설계 특성
- 작은 키-값 쌍(<10 KB)
- 고가용성과 확장성을 갖춘 대용량 데이터 지원
- 자동 확장 및 조정 가능한 일관성 수준
- 낮은 지연 시간

---

## 단일 서버 키-값 저장소
### 구현
- 메모리에 키-값 쌍을 저장하기 위해 **해시 테이블**을 사용합니다.
- 최적화 방법:
  - 데이터 압축
  - 접근 빈도가 낮은 데이터를 디스크에 저장

### 한계
단일 서버의 메모리에는 한계가 있으므로 확장성을 확보하려면 **분산 방식**이 필요합니다.

---

## 분산 키-값 저장소
**분산 키-값 저장소**는 데이터를 여러 서버에 분할해 저장하며, **CAP 정리**가 설명하는 트레이드오프를 고려해야 합니다.

### CAP 정리
1. **일관성(Consistency):** 모든 클라이언트가 같은 시점에 동일한 데이터를 봅니다.
2. **가용성(Availability):** 일부 노드가 중단되더라도 시스템이 모든 요청에 응답합니다.
3. **파티션 내성(Partition Tolerance):** 네트워크 파티션이 발생해도 시스템이 계속 동작합니다.

**트레이드오프:** CAP 정리에 따르면 세 가지 특성 가운데 동시에 두 가지를 선택해야 합니다.

<p align="center">
  <img src="./images/cap.png" alt="CAP" width="400">
</p>

#### 시스템 유형
- **CP 시스템:** 가용성을 일부 희생하고 일관성과 파티션 내성을 선택합니다. 예: 은행 시스템.
- **AP 시스템:** 일관성을 일부 희생하고 가용성과 파티션 내성을 선택합니다. 예: 최종 일관성 시스템.
- **CA 시스템:** 파티션 내성을 희생하고 일관성과 가용성을 선택합니다.

    **네트워크 장애는 피할 수 없으므로 분산 시스템은 네트워크 파티션을 견딜 수 있어야 합니다. 따라서 현실적인 분산 애플리케이션에서 순수한 CA 시스템을 구성하기는 어렵습니다.**

    분산 시스템에서는 파티션이 발생할 수 있습니다. 파티션이 발생하면 일관성과 가용성 사이에서 선택해야 합니다. 예를 들어 노드 n3가 단절되면 n1 또는 n2에 기록한 데이터를 n3로 전파할 수 없습니다. 반대로 n3에 데이터가 기록되었지만 아직 n1과 n2로 전파되지 않았다면 n1과 n2에는 오래된 데이터가 남아 있게 됩니다.

    <p align="center">
    <img src="./images/server-down.png"  alt="서버 장애" width="400">
    </p>
    
- CP 시스템을 선택한다면 데이터 불일치를 방지하기 위해 n1과 n2에 대한 모든 쓰기 작업을 차단해야 합니다.
- AP 시스템을 선택한다면 오래된 데이터를 반환할 가능성이 있더라도 시스템은 계속 읽기 요청을 받습니다. 쓰기의 경우 n1과 n2가 계속 요청을 받고, 네트워크 파티션이 해결되면 데이터를 n3와 동기화합니다.

## 시스템 구성 요소
### 1. 데이터 파티셔닝
- **기법:** 일관 해싱을 사용해 데이터를 여러 서버에 고르게 분산합니다.
- **장점:**
  - 서버 추가/제거에 따른 자동 확장
  - 가상 노드를 이용한 이기종 서버 지원. 서버의 가상 노드 수를 해당 서버 용량에 비례하도록 설정할 수 있습니다.

### 2. 데이터 복제
- 고가용성을 위해 데이터를 `N`개의 서버에 복제합니다.
- 서버 위치에서 링을 시계 방향으로 이동하면서 처음 만나는 N개의 서버를 선택해 데이터 사본을 저장합니다. 가상 노드를 사용할 때도 안정성을 높이기 위해 복제본이 서로 다른 실제 데이터 센터에 배치되도록 합니다.

    <p align="center">
    <img src="./images/data-replication.png" alt="데이터 복제" width="300">
    </p>

### 3. 일관성
데이터가 여러 노드에 복제되므로 복제본 사이의 동기화가 필요합니다.
- **쿼럼 합의(Quorum Consensus):**
  - `N`: 전체 복제본 수
  - `W`: 쓰기 쿼럼 크기. 쓰기가 성공한 것으로 간주되려면 W개의 복제본에서 쓰기 확인을 받아야 합니다.
  - `R`: 읽기 쿼럼 크기. 읽기가 성공한 것으로 간주되려면 최소 R개의 복제본에서 응답을 받아야 합니다.
  - **규칙:** `W + R > N`이면 강한 일관성을 확보할 수 있습니다.
  - W, R, N의 설정은 일반적으로 지연 시간과 일관성 사이의 트레이드오프입니다.

    <p align="center">
    <img src="./images/quorum-consensus.png"   alt="쿼럼 합의" width="400">
    </p>
    
    - R = 1, W = N이면 빠른 읽기에 최적화됩니다.
    - W = 1, R = N이면 빠른 쓰기에 최적화됩니다.
    - W + R > N이면 강한 일관성을 확보할 수 있습니다. 일반적으로 N = 3, W = R = 2를 사용할 수 있습니다.
    - W + R <= N이면 강한 일관성을 보장할 수 없습니다.

- **일관성 모델:**
  - **강한 일관성(Strong Consistency):** 읽기 연산이 가장 최근 쓰기 결과에 대응하는 값을 반환합니다.
  - **약한 일관성(Weak Consistency):** 이후의 읽기 연산에서도 최신 값을 보지 못할 수 있습니다.
  - **최종 일관성(Eventual Consistency):** 충분한 시간이 지나면 모든 갱신이 전파되어 모든 복제본이 일관된 상태에 도달합니다.


### 4. 불일치 해결
복제는 고가용성을 제공하지만 복제본 사이에 데이터 불일치가 발생할 수 있습니다. 버전 관리와 벡터 클록(vector clock)을 사용해 이러한 문제를 해결할 수 있습니다.
- **버전 관리:**
    - **벡터 클록**을 사용해 데이터 버전을 추적하고 충돌을 해결합니다.
    - 버전 관리란 각 데이터 변경을 새로운 불변 버전의 데이터로 취급하는 것을 의미합니다.
        <div>
        <img src="./images/consistent-server.png"   alt="일관된 서버" width="400">
        <img src="./images/inconsistent-server.png"   alt="불일치 서버" height="230">
        </div>
    
    - 서버 1과 서버 2가 같은 이름 값을 동시에 변경했다고 가정합니다. 이때 서로 충돌하는 두 값, 즉 버전 v1과 v2가 생깁니다.


- **벡터 클록(Vector Clock)**
    1. **구성:** 벡터 클록은 데이터 항목에 연결된 `[서버, 버전]` 쌍입니다. 한 버전이 다른 버전보다 이전인지, 이후인지 또는 서로 충돌하는지를 판별하는 데 사용할 수 있습니다.
        - 벡터 클록을 `D([S1, v1], [S2, v2], …, [Sn, vn])`으로 표현한다고 가정합니다. 데이터 항목 D가 서버 Si에 기록되면 시스템은 해당 서버의 버전 정보를 갱신해야 합니다.
        - 여기서 `D`는 데이터 항목, `Si`는 서버 식별자, `vi`는 서버 `Si`에 저장된 데이터의 버전 카운터입니다.

    2. **벡터 클록 갱신:** 서버에서 데이터 항목이 변경되면 다음과 같이 처리합니다.
        - 해당 서버가 벡터 클록에 이미 있으면 버전 카운터를 증가시킵니다.
        - 없다면 벡터 클록에 새 항목을 추가합니다.

    3. **충돌 탐지:**
        - **충돌 없음:** X의 모든 카운터가 Y의 대응 카운터보다 작거나 같으면 버전 X는 버전 Y의 조상입니다.
        - **충돌 있음:** 서로의 카운터를 비교했을 때 한쪽이 다른 쪽보다 항상 앞선다고 판단할 수 없다면 두 버전은 형제(sibling) 관계이며 충돌한 것으로 봅니다.

    4. **충돌 해결:** 충돌하는 형제 버전이 발견되면 애플리케이션별 병합 로직이나 클라이언트의 개입을 이용해 데이터를 조정합니다.

        <p align="center">
        <img src="./images/vector-clock.png"  alt="벡터 클록" width="500">
        </p>

- **과제:**
  - 클라이언트 로직이 복잡해집니다.
  - 갱신 횟수가 많아질수록 벡터 클록의 크기가 커질 수 있으므로 크기를 제한하기 위한 정리 전략이 필요할 수 있습니다.


### 5. 장애 처리

#### a. 장애 감지
다른 서버 하나가 특정 서버의 장애를 보고했다는 이유만으로 해당 서버가 중단되었다고 판단하기에는 부족합니다. 일반적으로 서버를 장애 상태로 표시하려면 최소 두 개 이상의 독립적인 정보원이 필요합니다.
- **가십 프로토콜(Gossip Protocol):**
    <div style="margin-left:3rem">
        <img src="./images/gossip-protocol.png"  alt="가십 프로토콜" width="600">
    </div>

    - 각 노드는 멤버 ID와 하트비트 카운터를 유지합니다.
    - 각 노드는 주기적으로 자신의 하트비트 카운터를 증가시킵니다.
    - 각 노드는 주기적으로 임의의 노드 집합에 하트비트를 보냅니다.
    - 미리 정의된 시간 이상 하트비트가 증가하지 않으면 해당 멤버를 오프라인으로 간주합니다.



#### b. 일시적 장애
- **슬로피 쿼럼(Sloppy Quorum):** 정상 노드를 사용해 일시적으로 서비스를 계속 처리합니다.
        <p align="center">
        <img src="./images/sloppy-quorum.png"   alt="슬로피 쿼럼" width="400">
        </p>

    - 장애를 감지한 후 시스템은 가용성을 유지하기 위한 메커니즘이 필요합니다.
    - 엄격하게 원래 복제본 집합의 쿼럼을 강제하는 대신, 해시 링에서 정상 상태인 서버 중 처음 W개를 쓰기에, 처음 R개를 읽기에 사용합니다.
    - 오프라인 서버는 건너뜁니다. 서버 하나를 사용할 수 없다면 다른 서버가 일시적으로 요청을 처리합니다.


- **힌티드 핸드오프(Hinted Handoff):** 오프라인 서버가 복구되면 중단 기간의 변경 사항을 따라잡도록 합니다.
    - 장애 서버가 복구되면 변경 사항을 다시 전달해 데이터 일관성을 회복합니다.

#### c. 영구 장애
- 복제본 사이를 효율적으로 동기화하기 위해 **머클 트리(Merkle Tree)**를 사용합니다.
    **머클 트리** 또는 해시 트리는 영구 장애 이후 복제본 간 불일치를 효율적으로 탐지하고 해결하기 위한 데이터 구조입니다.

- 동작 방식
    1. **구조:**
        - **리프 노드**는 개별 데이터 블록의 해시를 저장합니다.
        - **비리프 노드**는 자식 노드의 해시를 저장합니다.
        - **루트 해시**는 트리 전체 데이터의 결합된 상태를 나타냅니다.

    2. **머클 트리 구성:**
        - **1단계:** 키 공간을 버킷으로 나눕니다.
            
            <img src="./images/key-bucket.png"   alt="키 버킷" width="500">

        - **2단계:** 균등한 해싱 방식을 사용해 각 버킷의 키를 해싱합니다.

            <img src="./images/hash-key-bucket.png"   alt="키 버킷 해싱" width="500">

        - **3단계:** 각 버킷에 대해 하나의 해시를 만듭니다.
        
            <img src="./images/hash-bucket.png"   alt="버킷 해시" width="500">

        - **4단계:** 버킷 해시들을 결합해 상위 수준의 해시를 계산하고 최종적으로 루트 해시를 만듭니다.

            <img src="./images/merkel-tree.png"   alt="머클 트리" width="500">



    3. **동기화:**
        - 두 복제본을 동기화할 때 다음 절차를 사용합니다.
            - 루트 해시를 비교합니다.
            - 루트 해시가 같으면 두 복제본이 일관된 상태입니다.
            - 루트 해시가 다르면 자식 해시를 재귀적으로 비교해 불일치하는 버킷을 찾습니다.
        - 불일치하는 데이터만 동기화합니다.

- 장점
    - **효율성:** 불일치 데이터만 동기화하므로 데이터 전송량을 줄입니다.
    - **확장성:** 동기화 오버헤드를 낮게 유지하면서 대규모 데이터셋에 적용할 수 있습니다.
    - **신뢰성:** 복제본 간 데이터 일관성을 유지하는 데 도움이 됩니다.


### 6. 데이터 센터 장애 처리
- 서비스 중단 중에도 가용성을 유지할 수 있도록 데이터를 여러 데이터 센터에 복제합니다.

- 클라이언트는 `get(key)`와 `put(key, value)` 같은 단순한 API를 통해 키-값 저장소와 통신합니다.
- 코디네이터(coordinator)는 클라이언트와 키-값 저장소 사이의 프록시 역할을 하는 노드입니다.
- 노드는 일관 해싱을 사용해 링 위에 분산됩니다.
- 시스템은 완전히 탈중앙화되어 있어 노드 추가와 이동을 자동화할 수 있습니다.
- 데이터는 여러 노드에 복제됩니다.
- 모든 노드가 동일한 책임 집합을 가지므로 단일 장애점이 없습니다.
